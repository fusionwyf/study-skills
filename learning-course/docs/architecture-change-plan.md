# learning-course 架构更改计划

日期：2026-10-11  
状态：待实施；本文件不代表代码已经完成整改。

本文依据当前工作区的架构审阅制定，作为重构参考和工程验收依据。`docs/` 不属于 skill 的功能协议，不参与 create、continue、export 的读取路由，不要求日常教学 Agent 读取，也不作为运行时能力登记源。

本次只编写计划。执行阶段按本计划逐步修改实现和功能文档，已有未提交改动应先核对并保留。

## 1. 目标与范围

目标是让“作者契约 → 模块选择 → 配置与依赖 → 初始化 → 学习记录 → 校验与导出”形成完整流程，使 Agent 按功能文档操作即可得到可验证的课件。

保留现有方向：

- 课程状态、可读计划、原始反馈与 Agent 评估分开。
- `kit/` 维护共享资产源，课程 `assets/kit/` 为生成物。
- L0–L5 分层、Token 主题和 CSS layer。
- 语义 HTML 与稳定的 `data-*` 作者契约。
- 题目共享状态与记录逻辑，可视化通过适配器扩展。
- 单文件经典脚本产物，支持 `file://` 分发；第三方依赖支持明确的 CDN 与离线模式。

本次不新增学科模型，不开展整页 LessonSpec 生成，不自动升级已有课程，不扩充大量组件。`course.yaml` v3 和 mastery 升级边界保持现有契约；页面记录中有误导性的辅助信息允许纠正，不能继续以逐字节等价为由保留错误语义。

## 3. 功能文档的职责

| 文件 | 唯一主要职责 | 应迁出或删除的重复内容 |
|---|---|---|
| `SKILL.md` | create/continue/export 工作流、读取路由、完成条件 | 完整分层说明、重复组件写法、工程重构历史 |
| `references/lesson.md` | 页面语义、题目与内容作者契约、教学设计 | 构建管理和资产安装细节 |
| `references/assets.md` | 已有能力的选择、同步、课程扩展接线和验收 | 逐组件完整 HTML 示例、重复主题架构 |
| `references/render.md` | 动态模型、状态绑定、可视化配置及后备 | 再次解释全部分层、代码块和公式基础写法 |
| `references/state.md` | 课程状态、阶段和恢复 | 不引入资产实现细节 |
| `references/export.md` | 导出模式、等待条件、失败处理和视觉检查 | 不重复组件契约 |

规则的规范性文本只保留一处，其余通过相对链接引用。必要的入口提醒可以保留，但不能复制整段协议。能力清单由模块描述符生成，不依赖 docs 中的表格。

`docs/` 只保存重构设计、计划、历史决策和验收记录。可以在实施时修正示例、补充适用版本，不能把旧设计全部追写成“当前已实现”，也不能把 docs 接入 skill 的日常读取路由。

## 4. 实施阶段

### P0：建立可追踪基线

改动范围：测试与验收材料，必要的版本说明。

1. 核对已有未提交改动，建立当前模块、公共接口、生成物和兼容路径清单。
2. 在临时课程中固定 A1–A6 的失败场景，新增能证明外部行为的回归检查。
3. 记录当前测试通过、失败、跳过和未验证项，不能用历史“全量通过”替代本次结果。
4. docs 中旧计划作为历史保留；本计划负责此次实施范围，不合并或覆盖旧计划。

验收：有可重复的失败用例；明确每项问题对应的实现位置和验证方法；保留原有工作区改动。

### P1：配置、描述符与构建流程

对应问题：A1、A2。

主要文件：`kit/build/kit.py`、`kit/core/config.js`、模块描述符、初始化脚本、构建测试。

1. 定义并校验模块描述符：唯一 ID、层级、presence、依赖、文件列表、检测规则及 vendor 引用。重复 ID、缺失依赖、循环依赖、缺失文件和不合法层级关系必须失败。
2. 用 HTML 解析结果执行通用检测。最低支持标签、class、属性存在、属性等值和必要的父子关系；不支持的选择器必须报错，不能静默漏检。
3. 数学定界符检测作为明确的检测类型，检查适用文本节点，排除代码、脚本与跳过区域。不要将特殊情况塞入所有选择器的分支。
4. 同步时记录模块被纳入的原因，区分 core、页面触发、显式启用和依赖引入。
5. 从课程 `config.json` 构建运行时配置并嵌入生成的 JS；页面 `#kit-config` 在其上覆盖。优先级为默认值 → 课程配置 → 页面配置；旧全局兼容的优先级与移除条件另行明确。
6. 配置错误和未知显式模块必须报错。同步后修改配置需要再次 sync，功能文档必须说明。
7. 构建与同步使用同一份已验证描述符快照，避免 manifest 选模块与源文件打包采用不同状态。
8. 校验全部输入后再写出文件；失败时不留下部分更新的包。sync 应可重复执行，不能反复改变相同 HTML。

验收：

- `[data-animate]` 能自动纳入动画模块。
- 新增使用受支持选择器的模块，无需修改检测器即可生效。
- 合法的多 class、单双引号写法被一致识别；示例文本不误启用模块。
- 课程主题、数学宏、代码主题配置在 `file://` 和 HTTP 下生效，页面覆盖优先级正确。
- 错误描述符与配置明确失败，重复同步产物稳定。

### P2：统一第三方依赖与离线资源

对应问题：A6、A10 中的依赖登记。

主要文件：描述符、`kit/core/loader.js`、`kit/vendor/manifest.json`、chart/spatial、主题引擎、构建脚本。

1. 模块描述符声明依赖 ID 与版本需求；vendor 清单保存精确版本、资源路径、CDN、校验信息和许可证。相同 vendor 的版本冲突在构建时失败。
2. 构建生成唯一运行时 vendor 注册表，删除 loader 与可视化中的重复版本和加载定义。
3. 所有组件统一调用 `kit.need(id)`；JS、CSS、前置依赖、去重、超时与失败处理由加载器负责。
4. CDN 模式使用验证过的固定版本及适用资源的 SRI；禁止占位 SRI。离线模式复制实际依赖文件、字体、主题 CSS 和许可证，路径与产物位置一致。
5. 离线所需资源缺失时构建失败，不能生成宣称可离线却只有路径的包。
6. lock 记录 vendor 来源、版本和本地文件哈希。明确 CDN 失败的降级策略，不能在离线模式静默访问网络。
7. chart/spatial 通过统一加载器，主题适配读取 Token；官方高亮主题仍使用固定版本官方资源。

验收：同一 vendor 并发请求只加载一次；CDN 成功、失败、超时与离线成功、资源缺失分别有覆盖；离线浏览器验收不出现网络请求；Plotly 等版本与清单一致；失败后文字/表格后备可读。

### P3：统一初始化与就绪协议

对应问题：A3、A8 中未采用的 registry。

主要文件：registry、ready、构建入口、内容/外壳/题目/可视化模块。

1. 构建入口先登记全部活动模块，再按依赖顺序初始化。采用单一模块注册接口，现有模块改为通过该接口提供初始化函数，停止各自独立抢跑。
2. 初始化函数可以返回 Promise；ready 管理器等待其完成。依赖模块完成后才能初始化调用方，第三方资源加载与首轮渲染纳入等待。
3. 全局状态区分 pending 与 settled；settled 携带 ready、failed 和降级信息。保留 `kit:ready` 时明确它表示流程完成，不自动等于全部成功。
4. 统一增强元素状态与失败原因。模型初始化、代码高亮、数学和图形失败必须能被验收读取，不能只写控制台或旧私有属性。
5. 定义初始化超时、失败后的可读后备、重入防护和资源释放。扩展初始化也纳入同一流程。
6. 兼容事件只在统一流程完成后派发，避免提前标记旧就绪变量。

验收：慢速渲染期间全局不提前 ready；所有活动模块完成或明确失败后才发布最终结果；失败信息完整；重复初始化不重复绑定事件；无脚本后备保留。

### P4：校验与导出闭环

对应问题：A4、A3 中的导出行为。

主要文件：`kit.py check`、`validate_assets.py`、`validate_course.py`、`export_pdf.py`、相关 tests。

1. 校验 lock 结构、支持的格式版本、必需产物、模块存在性、依赖闭包、vendor 文件和文件哈希；空或不完整清单必须失败。
2. 区分“现有产物完整”与“相对当前源需要重新同步”。已有课程使用不同 Kit 版本不应被不加说明地判为损坏。
3. 通过描述符的能力映射核对页面所需模块。每个可视化 kind 必须有实现，不能以 `viz.core` 代替；覆盖 code、math、question、animation 和课程扩展。
4. 通用 DOM 与 JSON 契约尽量复用。Python 和 JS 各自必须保留的检查通过同一组有效/无效 fixtures 校准；新增 kind 不应需要修改多处硬编码列表。
5. 导出工具等待统一运行时结果并检查失败元素。默认存在渲染失败时停止导出并说明原因；若允许明确的后备导出，提供显式选项并记录结果。
6. 超时报告未验证，不能把“PDF 文件非空”作为成功渲染证明；保持 student/review 模式语义。

验收：缺 kind、未知模块、缺依赖、空 lock、被修改产物、缺离线资源均失败；合法包通过；慢速加载仍正确导出；失败与超时不误报完成；实际检查导出分页、公式、图表和裁切。

### P5：纠正学习记录的证据语义

对应问题：A5；可在 P1–P4 之外独立实施。

主要文件：question、records、`references/lesson.md`、`scripts/update_progress.py` 与共享记录解析/测试。

1. 页面只记录可观察行为：原始答案、尝试次数、点击提示、AI 引导提示、答案揭示和逐轮对话。
2. “未使用页内提示”不能自动变成 `independent`，也不能写为“学习者自述”。学习者自述只能来自实际填写或聊天说明。
3. 区分页面观察、学习者自述和 Agent 判断；外部辅助不可观测时保持未确认，提交或答对本身不能证明独立完成。
4. independence 在定稿阶段按共享记录契约评估，mastery 更新继续依赖 finalized record。共享契约是权威来源，不在 lesson 文档复制另一套定义。
5. 调整记录导入解析器以接受纠正后的字段，同时保留旧记录阅读能力，不改写历史定稿记录。
6. 原始答案保真与辅助字段语义分别验收。开放题和对话不能先 trim 再作为原话保存；判分规范化可以使用独立副本。

验收：未点提示不能自动支撑独立迁移；使用提示、AI 引导和答案揭示均可回查；多轮保留问题、原话和顺序；旧记录可读；导入到定稿及状态更新的整条流程通过共享契约校验。

### P6：补齐课程扩展与组件接口

对应问题：A7、A8。

主要文件：构建、registry/store/viz、question、nav、`references/assets.md`。

1. 为课程扩展定义最小声明：ID、入口 JS、可选 CSS、依赖及提供的能力。构建扫描显式登记的课程扩展，将它们纳入生成物、lock 和初始化顺序。
2. 明确模型、renderer、kind 三类接口：模型负责 initialState/reduce/derive；renderer 负责视图；kind 负责 validate/render 和适用的 update/destroy。不能要求所有扩展实现同一组方法。
3. 支持自定义 kind 的能力登记与验证来源，不需要手工修改全局 adapters 文件。扩展在状态容器首次初始化前完成注册。
4. 将题型特有的控件、答案采集、判分和揭示处理放入题型适配器；公共题目状态机、提示、反馈、记录和打印继续共享。先迁移现有六类，不新增产品题型。
5. 用测试专用题型验证扩展接口，避免为了演示扩展而增加长期维护的组件。
6. 实现 nav 的课程首页、上一课/下一课和课时列表；导航数据由构建或索引阶段生成，提供无脚本链接后备，避免另设手写导航源。
7. 明确相近能力的选择规则：静态表格用原生 table，模型数据表用 viz table；静态流程图用 Mermaid，状态绑定或交互过程使用对应 kind。共存不要求合并实现。

验收：课程模型与自定义 kind 可在 file/HTTP 下运行，加载顺序、更新、销毁、失败后备可检查；测试题型无需修改公共状态机即可接入；现有六题型行为回归通过；导航完整且无脚本可用。

### P7：登记去重、功能文档收敛与最终验收

对应问题：A9、A10；在接口稳定后实施。

1. 明确源与生成视图：module 描述符、vendor 清单和课程扩展声明为源；manifest/catalog/能力映射为生成物。删除生成器保留旧 assets/roles/delivery 数据的隐式继承。
2. 迁移仍使用旧 adapters 路径的校验逻辑，移除错误的可编辑指引；兼容入口只转发，不保留第二套能力系统。
3. fixtures 区分内容源、手写课程定制与生成物。删除旧运行时代码副本，生成物按测试需要在临时目录构建，不靠旧资产副本维持测试通过。
4. 按第 3 节分工精简 SKILL 与 references；明确流程：制作/修改课件 → sync → build_index → check → strict/pedagogical validation → 必要的浏览器与导出检查。
5. 区分课程验收与 skill 维护检查；统一完成条件中的命令数量、初始化模板占位符和多课维护要求。
6. 已实现能力、需要课程扩展的能力和不可用能力必须清楚区分。Chart.js、Cytoscape、vis-timeline 等未提供统一模块时，不能让 agent 把它们当作开箱即用能力。
7. docs 保持重构参考定位；修正 `kit.ready(id)` 等失效示例、标明历史适用版本和未实施内容。日常运行不依赖 docs。
8. 检查 LessonSpec、旧 alias 与兼容接口的真实调用方；有调用方的保留并测试，无调用方且不属于保留契约的删除。不能仅凭文件名判断冗余。

验收：功能文档没有冲突的规范；按文档可完成新建、增加新模块课件、续学记录和导出；不存在失效命令与不存在的组件路径；共享模块与能力登记只有一个来源；docs 未被加入功能读取路由。

## 5. 顺序与交付方式

主线：P0 → P1 → P2 → P3 → P4 → P6 → P7。P5 可独立推进，但 P7 前必须完成。

优先交付配置/构建、就绪/校验和证据语义；组件接口整理在基础流程可靠后进行。每阶段交付实现、对应功能文档与必要回归验证，保持可单独审阅与回退。

如实施中改变配置、记录输出、lock 或公共接口，先列出兼容影响，再同步调用方。原始记录与课程内容不因资产更新被静默改写。生成物只通过明确的同步操作更新。

## 6. 最终完成标准

- 配置从课程源进入运行时，页面覆盖和重新同步规则明确。
- 模块选择、依赖和构建不再依赖逐模块特殊分支；错误输入明确失败。
- vendor 来源唯一，版本一致，离线资源完整且不访问网络。
- ready 代表全部活动模块已完成或已明确失败；异步渲染与课程扩展被纳入。
- 校验能够发现功能缺失；导出等待并检查实际运行结果。
- 页面观察不冒充独立性判断或学习者自述；原始答案和多轮记录保真。
